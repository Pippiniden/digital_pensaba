# エンジン/UI/CPU の実装メモ

AGENTS.md §5 設計ルール 4(render/画像)・5(演出キュー)・9(CPU) の詳細。

4. **`render()` rebuilds `#app` from scratch every time**, through `setHTML(el, html)` (common.js), which moves already-loaded `<img>` elements with the same `src` + class + style from the old DOM into the new one, so portraits do not flicker or get re-decoded on every phase change (`.mc-o` / `.mc-i` are matched without style). CSS animations restart whenever an element is rebuilt or moved, so the magic circle spins via the Web Animations API (`syncMagicCircle` in game-ui.js, `startTime=0` so the angle depends only on the document clock) and the NP pulses (`.gauge.np.full i`, `.sk.np.ready`) get a clock-based negative `animation-delay` from `syncPulses`; both run at the end of `render()`. Do not put infinite CSS animations on elements that `render()` rebuilds without doing the same. Use `setHTML` / `replaceHTML` instead of `innerHTML` / `replaceWith` when redrawing anything with images (`redrawSvt`, `redrawLane`, `redrawRoster` do). Image URLs that failed once go into `IMG_BAD` and are skipped by `imgCandidates` from then on (so a missing `{id}_card.webp` is not re-requested on every render). Do not add `loading="lazy"` to these images (it causes a blank frame on each re-render). Events are delegated on `document` (`data-a` = game action, `data-ui` = UI action; the editor uses `data-act` / `data-p`). Do not attach listeners directly to elements.
5. **Effects go through `FXQ`** (`fxEmit`/`say`), and `fx.js` plays them on `#fx`. Rule processing does not wait for effects to finish; only the CPU waits via `fxBusy()`.
   - Event types (`ev.t`): `say` (line bubble), `dmg` (damage number / "無効" text), `cutin` (ultimate), `phase` (banner over `.stage`; `big` for turn start / game end), `banner` (chain banners), `roll` (spinning pencil over a portrait, lands on `f`; shows `n` actions or the `cmd` card), `atk` (command card zooms to the stage center and flies to `tgt`), `pop` (text over a portrait, e.g. ascension), `skill` (panel over `.stage` with the skill name, user, picked target and one line per effect; emitted by `doSkill`). Any event may carry `w` to override the wait before the next one (e.g. `say(u,'attack',{w:250})` overlaps the bubble with the attack card). Helpers in engine.js: `say`, `phaseFx`, `rollFx`.
   - Pencil faces (`u.face`, the die / command badge on a portrait) are cleared for every unit in `endPhase` and at the start of `rollActs`, so a card never lingers into the next turn.
   - Knock-outs are shown late on purpose: `retreat()` (engine name for KO) sets `u.out` at once but only queues the uid in `KO_PEND`; `flushKo()` — called at the end of `resolveDamage`, `doSkill` and `endPhase`, before `checkWin` — emits one `ko` event and the `defeat` lines. Until then `stepHold` keeps the card at HP 0 but not darkened, so later attacks (overkill hits, which emit a `dmg` with `over:true`) still play on it. If you add another place that can KO a unit, call `flushKo()` after it.
   - Roll results are hidden until the roll animation lands: `rollFx(uid,f,{keys})` adds keys to `FXHIDE` (`'f:<uid>'` = the portrait's die badge / alloc control, `'r:<idx>'` = that card in the command lane); `reveal()` in fx.js deletes them and redraws. `rollBadge` / `ctlHTML` / `laneHTML` check `FXHIDE`.
   - NP gauge and buffs/debuffs lag the same way: `snapPre()` (start of `act()`) records the displayed state, `syncU(u)` emits `{t:'sync',uid,hp,np,fx}` after a change (deduped by `SYNCED`), and `stepHold` applies it when played. `FXHOLD[uid]={hp,np,fx,out,ko}`; `shown(u)` in `game-ui.js` returns it. When you change NP / `fx` outside `applyOne`, call `syncU(u)`. The 'end' prompt shows "ダメージ処理中" while `fxBusy()` (`UI.defer` re-renders when the queue empties).
   - Displayed HP lags behind `G` on purpose: a `dmg` event carries `hp0` (before), `hp` and `out` (after). `fxEmit` puts the unit into `FXHOLD` at `hp0`; `fx.js` (`stepHold`) advances it per event and redraws only that card (`redrawSvt`); when the unit has no more queued `dmg` events the hold is removed. Cards read HP / knocked-out state via `shown(u)` in `game-ui.js`. Any new code that changes HP through damage must go through `dealDamage` (or emit the same fields) or the bar will jump.
9. **The CPU does not know the rules.** Tune strength via `cpuSkillScore` (when to use skills), `cpuBestTarget` (attack target) and `cpuAlloc` (action allocation). `hard`/`expert` (`cpuHard()`) also use `cpuThreatTarget`, hold damage ultimates weaker than `turnPower()` in `cpuUltUser`, allocate actions by expected damage (`cpuAllocEV` / `allocEV`: per-action face averages incl. atk buffs and crit expectation, Buster Chain probability, Brave Chain extra attack, `ASC_VALUE` for an ascension face — so a weak unit's Brave Chain loses to mixing in a unit with roughly twice its per-action damage), and in the team rule time evade/invul skills to enemy ultimates (`cpuGuardScore`: top priority when an enemy has NP 100 and the skill covers the likely target, otherwise held until HP < 35%); `hard` and `expert` pick the attack target with `cpuMcTarget` (a Monte Carlo lookahead; rollout/turn counts are `MC_R_*` / `MC_T_*` per level). `CPU_LOOKAHEAD=false` turns `hard`'s lookahead off (= the old `hard` = `cpuThreatTarget`; **sim.js sets it false** so balance runs stay fast and comparable), and `cpuInRollout` makes `hard` inside a rollout use `cpuThreatTarget` (no nesting). `cpuNextSkill` uses a score threshold of 3 for `hard`/`expert` (2 for `normal`). In the simple rule `expert` also picks (party of 1) also the skill-phase move with `cpuMcSkill` (it only overrides the `hard` move when it wins by `MC_MARGIN` (off in the team rule)). Both go through `cpuMcScores` (Monte Carlo: copies `G`, plays each candidate out `mcRollouts()` times with both sides `hard` (no lookahead), then restores `G` and the FX state — keep that save/restore complete if you add new global engine state). When you add a new effect to `FX`, also add a score to the `switch` in `cpuSkillScore` (otherwise it counts as worth 0).
